AIに仕事を任せるために、僕がやっていること


AIに仕事を任せるとき、本当に大事なのは「プロンプト力」ではない。

プロンプトというのは、AIに出す指示文のこと。

「こういう条件で、こういう文章を作ってください」とお願いする文章だと思えばいい。

もちろん、プロンプトの書き方は大事。

でも、僕が実際にXの投稿づくり、ジモティーの求人投稿、LP制作、法人研修の資料づくりをAIに任せてきて感じているのは、もっと手前の準備でほぼ勝負が決まるということ。

ここでいうAIは、ただチャットで返事をするだけのAIではない。

ファイルを読んで、文章を作って、画像の指示文を作って、決めた場所に保存するAIのこと。

いわゆるAIエージェントと呼ばれるものだけど、難しく考えなくていい。

AIエージェントなんて言葉を聞くと、急にエンジニア向けの話に聞こえるかもしれない。

でも、簡単に言うと「こちらが用意した資料を読んで、作業までしてくれるAI」だと思えばいい。

人に仕事を頼むときも、いきなり「いい感じにやって」だけだと困る。

目的、見本、ルール、保存場所を渡した方が動きやすい。

AIでも同じ。

結論から言うと、AIに仕事を渡すときにやることは毎回同じ。

1. 前提知識を用意する
2. 良い見本を用意する
3. ファイルに分ける
4. AIが読む順番を決める
5. 保存先と確認方法まで決める

これだけ。

ただ、これを聞いても、多くの人はまだピンとこないと思う。

「前提知識って何？」
「良い見本ってどこに置くの？」
「ファイルに分けるって、実際どういう形？」

ここが曖昧なままだと、AIに何度お願いしても、その場限りの結果で終わる。

だから今回は、僕が実際にどういうファイル構造でAIに仕事を渡しているかを、かなり具体的に見せる。

ファイル構造というと少し硬いけど、要するに「どの資料を、どの棚に置くか」という話。

会社の共有フォルダで、契約書、請求書、写真、議事録を全部同じ場所に置いたら探しにくい。

それと同じで、AIに読ませる資料も棚分けしておく。

一部の実アカウント名や個人名は公開用に伏せるけど、構造は実際に使っているものにかなり近い。

まず全体像はこう。

```text
Desktop/
|-- X運用/
|-- jmty-workspace/
|-- LPデザイン/
`-- AI法人研修/
```

この4つは、やっている仕事が全部違う。

Xは投稿の下書きと図解画像。
ジモティーは求人投稿文とバナー画像。
LPは申し込みページのこと。ページ内のまとまりごとの原稿、画像の指示文、ページ用の画像。
法人研修は講座概要、スライド案、講師台本、演習データ、配布資料。

でも、構造の考え方はほぼ同じ。

英語のフォルダ名が出てくるけど、ここも難しく考えなくていい。

`inputs` は「AIに読ませる材料」。
`samples` は「こういう感じにして、という見本」。
`outputs` は「AIが作ったもの」。
`runtime` は「作業中に出るメモやログ」。

そんな意味で使っている。

```text
仕事用フォルダ/
|-- inputs/ or accounts/       # AIに読ませる前提知識
|-- samples/ or templates/     # 良い見本・型・画風
|-- skills/                    # AIが読む手順書
|-- apps/ or scripts/          # 実行する仕組み
|-- outputs/ or runtime/       # 作ったもの・作業ログ
`-- docs/                      # 引き継ぎ・運用メモ
```

これがめちゃくちゃ大事。

AIに「作って」と頼む前に、AIが読める資料棚を作る。

資料棚の中に、前提知識、良い見本、ルール、手順、保存先、確認方法を置く。

そうするとAIは、毎回ゼロから考えるのではなく、その仕事の背景を読んで動けるようになる。

事例1: X運用

X運用のフォルダは、ざっくりこうなっている。

```text
X運用/
|-- private/
|   `-- x-post-writer/
|       |-- accounts/
|       |   |-- ai_putaro.md
|       |   |-- _sample_account.md
|       |   `-- gutaraaikatuyou/
|       |       |-- gutaraAikatuyou.md
|       |       |-- design-guide.md
|       |       |-- character-prompt.md
|       |       `-- infographic-rules.md
|       |-- scripts/
|       |   |-- scheduled_draft_pipeline.py
|       |   |-- draft_generation_schema.json
|       |   |-- fetch_bookmarks.py
|       |   |-- x_metrics_collector.py
|       |   `-- preview/
|       `-- SKILL.md
|
|-- public/
|   `-- x-post-writer-public/
|
|-- runtime/
|   |-- x-post-writer/
|   |   |-- draft-metadata/
|   |   |-- image-prompts/
|   |   `-- logs/
|   |-- x-post-images/
|   |   `-- logos/
|   `-- playwright-x-profile/
|
|-- launchd/
`-- docs/
```

ここで一番大事なのは、見せていいもの、見せないもの、作業中に出るものを分けていること。

`private` には、実アカウントの情報や実運用に必要な設定を置く。

`public` には、人に見せてもよいサンプルコードや公開用の設定だけを置く。

`runtime` には、実行中に出てくる作業ログ、下書きの管理情報、画像を作るための指示文、生成画像などを置く。

runtimeという言葉も、初めて見ると分かりにくいと思う。

僕の中では「作業中に出てくる一時置き場」くらいの意味で使っている。

料理で言うと、レシピ本が `inputs`、完成した料理が `outputs`、調理中に出るメモや途中経過が `runtime` みたいな感じ。

つまり、最初から「人に見せていいもの」と「実運用だけで使うもの」と「実行結果」を分けている。

これを分けておかないと、AIが作業するときに、見なくていいログを読んだり、公開してはいけない実アカウント情報を混ぜたりする。

X運用でAIに渡している前提知識は、たとえばこういうファイル。

```text
accounts/<アカウント名>/
|-- account.md              # 目的、読者、案内先、商品、口調
|-- design-guide.md         # 図解画像の配色、余白、見せ方
|-- character-prompt.md     # キャラクター画像のルール
`-- infographic-rules.md    # 図解投稿の構成ルール
```

実際のアカウント情報ファイルには、こういう内容を入れている。

- アカウントの目的
- ターゲット
- 口調
- キャラクター
- 最後に案内したい場所
- 売りたい商品
- よく使う表現
- 使わない表現
- 過去に反応がよかった投稿
- 図解の配色
- 画像生成時の禁止事項

これを読ませてから投稿を作らせるから、AIは「どこにでもありそうなAI投稿」ではなく、そのアカウントの背景に寄せた下書きを作れる。

さらに `draft_generation_schema.json` のような、AIの返し方を決めるファイルも置いている。

ここで出てくる `schema`、つまりスキーマという言葉も、聞き慣れない人が多いと思う。

簡単に言うと「記入用紙の型」みたいなもの。

名前、住所、電話番号を書く申込書があると、みんな同じ形で情報を書ける。

それと同じで、AIにも「本文はここ」「採用理由はここ」「画像の指示文はここ」と返す形を決めている。

これも地味に重要。

AIに自由に書かせると、毎回返ってくる形が変わる。

でも、最初から「下書き本文」「採用理由」「画像の指示文」「作らなかった理由」のように形を決めておくと、その後の保存、確認、画像作成、報告までつなげやすくなる。

つまり、X運用でやっていることはこう。

```text
ブックマーク投稿
    ↓
アカウント情報を読む
    ↓
参考投稿を分析する
    ↓
アカウント用の下書きに変換する
    ↓
図解画像の指示文も作る
    ↓
保存場所や作業用フォルダに残す
    ↓
確認用ページのリンクや画像の指示文を通知する
```

ここでAIに渡しているのは「バズる投稿を書いて」という一文ではない。

アカウントのキャラ、読者をどこへ案内するか、過去にうまくいった型、図解のルール、返し方の型、保存先まで渡している。

だから同じAIでも、毎回の出来が安定する。

この運用には、下書きを確認するためのアプリも作っている。


このアプリは、AIに投稿を考えさせるためのチャット画面ではない。

AIが作った下書きを、人間が確認し、直し、採用するための操作画面。

画面の左側には、アカウントと下書き一覧が並ぶ。

下書き、元投稿、分析のように表示対象を切り替えられるし、画像あり・画像なしの絞り込みや検索もできる。


元投稿タブでは、参考にした投稿をそのまま保存するだけではなく、なぜ伸びたのかを分析している。

たとえば、フック。

フックというのは、投稿の最初で読者の足を止める一言のこと。

釣り針みたいに、読者の注意を引っかける部分だと思えばいい。

他にも、投稿の形、数字の使い方、比較があるか、手順で説明しているか、最後に読者へしてほしい行動があるかを見る。

こういう要素を分解しておくと、AIは「なんとなく似せる」のではなく、構造を再利用できる。

中央には、実際に投稿されるスレッドが表示される。

1投稿ずつ本文、文字数、リプの並び、投稿前チェックの結果が見える。


右側には、操作ボタンを置いている。

- 投稿前チェック
- 採点
- 文字数チェック
- 本文AI修正
- 編集
- リプ追加
- メモ保管場所への保存
- 投稿済み状態への変更
- X投稿への移動


AI修正も、ただ「もっと良くして」ではなく、下書き全文を見せたうえで修正指示を入れる形にしている。

たとえば「冒頭をもっと自然にする」「結論を先に置く」「公開情報だけで書く」のように、人間が判断した修正方針をAIに渡す。

画像の指示文やアカウント設定まで毎回触らず、本文だけを直せるようにしている。

つまり、このアプリがやっていることは「AIに作らせること」ではなく、「AIが作ったものを運用に乗せること」。

裏側では、`accounts/` のアカウント情報、`runtime/` の下書きの管理情報、画像の指示文、投稿ログを読み書きしている。

アプリの画面は、そのファイル群を人間が扱いやすい形にしているだけ。

でも、この「だけ」がかなり効く。

チャット欄に生成結果が流れていくだけだと、どれを採用したのか、どこを直したのか、投稿済みなのかが曖昧になる。

アプリにすると、AIが作ったものを「下書き一覧」「投稿前チェック」「編集履歴」「投稿済みかどうか」として管理できる。


投稿後は、下書きとメトリクスを紐づける。

メトリクスというと大げさだけど、要するに「反応の数字」のこと。

どの型が反応されたのか。
どの投稿が保存やクリックにつながったのか。
どのアカウントで何本投稿済みなのか。

この結果が次の下書き作成の前提知識になる。

だから、X運用は単発の文章づくりではなく、毎日の投稿作業になる。

事例2: ジモティー求人投稿

ジモティーの自動化は、さらにわかりやすい。

求人投稿文と画像を、毎週アカウントごとに作り直す仕組み。

構造はこう。

```text
jmty-workspace/
|-- inputs/
|   |-- jmty_factory_cases/
|   |   `-- 2026-02_案件一覧.md
|   |-- jmty_remote_samples/
|   |   `-- 2026-02_在宅職種リスト.md
|   |-- jmty_post_style_samples/
|   |   |-- factory/
|   |   `-- remote/
|   `-- jmty_image_prompt_templates/
|       |-- README.md
|       |-- factory_自動車製造スタッフ01.md
|       |-- remote_在宅01.md
|       |-- common_gafoo_vector_minimal.md
|       `-- _previews/
|
|-- .agent/
|   `-- skills/
|       |-- jmty/
|       |   `-- jmty-posts/
|       `-- nanobanana-banner-gen/
|           `-- scripts/
|
|-- apps/
|   `-- jmty-control/
|
|-- outputs/
|   |-- jmty-weekly/
|   |   `-- current/
|   |       |-- <アカウント名>/
|   |       |   |-- 工場の投稿文章.md
|   |       |   |-- 工場_画像プロンプト.md
|   |       |   |-- 工場.jpg
|   |       |   |-- 在宅1の投稿文章.md
|   |       |   |-- 在宅1_画像プロンプト.md
|   |       |   |-- 在宅1.jpg
|   |       |   |-- 在宅2の投稿文章.md
|   |       |   |-- 在宅2_画像プロンプト.md
|   |       |   |-- 在宅2.jpg
|   |       |   `-- 画像プロンプト一覧.md
|   |       |-- tasks.json
|   |       |-- rotation_report.md
|   |       `-- _improvement_reports/
|   `-- jmty-gui/
|       |-- sheet_cache.json
|       |-- image_validation.json
|       `-- approvals.json
`-- README-jmty-weekly-automation.md
```

ジモティーで大事なのは、投稿文と画像を「アカウント別」「求人種別別」に分けていること。

1アカウントの中に、工場、在宅1、在宅2がある。

それぞれに、

- 投稿文章
- 画像を作るための指示文
- 画像

がセットで置かれる。

ここでいう画像を作るための指示文は、画像プロンプトのこと。

プロンプトという言葉をまた使うと難しく見えるけど、要するに「こんな画像にして」とAIに伝える注文書。

美容室で「短めで、前髪は残して、明るすぎない色で」と伝えるのと同じで、画像AIにも希望を言葉で渡す。

この構造にしておくと、AIも人間も迷いにくい。

「このアカウントの在宅1だけ直して」
「工場画像と投稿文が合っているか確認して」
「Google Driveに入れる前に画像だけ確認して」

こういう指示が出せる。

しかも、ジモティーでは操作画面も作っている。


ジモティーのアプリは、毎週の更新作業をまとめて進める画面として作っている。

画面上部には、主要なタブが並んでいる。

- ダッシュボード（状況を一覧で見る画面）
- 投稿文管理
- 地域・ローテーション（投稿地域の入れ替え）
- 画像生成
- 画像の指示文管理
- 実行ログ
- 見本管理

ダッシュボードという言葉も、車の運転席をイメージすると分かりやすい。

スピード、ガソリン、警告ランプが一目で分かる場所。

このアプリでも同じで、今どこまで進んでいるか、どこで止まっているかを一目で見るための画面にしている。

ローテーションは「順番に回す」という意味。

同じ地域ばかりに投稿するのではなく、投稿地域を順番に入れ替えるための仕組み。

このタブ構成にしている理由は、ジモティー運用が1つの作業ではないから。

地域を決める。
投稿文を作る。
画像を作るための指示文を作る。
画像を生成する。
投稿文と画像が合っているか確認する。
Google Driveに入れる。
スプレッドシートに反映する。
失敗したところだけやり直す。

これらを毎週、複数アカウント分やる。

チャットだけでやると、どの工程まで終わったのかがすぐ分からなくなる。

だからアプリでは、毎週の処理がどこまで進んだかと、実行ログを最優先で見えるようにしている。

ダッシュボードでは、週次一括実行、途中から再実行、ログ確認ができる。

一括実行を押すと、投稿地域の入れ替え、投稿文づくり、画像づくり、Google Driveへの保存、スプレッドシートへの反映までの流れを進める。

途中で失敗した場合は、最初から全部やり直すのではなく、途中から再実行できるようにしている。

これがかなり大事。

10アカウント分のうち、1アカウントの在宅2画像だけ失敗したときに、全部を最初から回す必要はない。

失敗した工程だけを見つけて、そこだけ直せるようにする。

投稿文管理タブでは、工場、在宅1、在宅2の投稿文をまとめて扱う。

できることは、たとえばこう。

- 投稿文の一括確認
- 投稿文の一括再作成
- 確認NGだけAI再作成
- スプレッドシートからの読み込み
- 未反映の投稿文をシートへ反映
- 基本情報や作成ルールの確認


ここでも、AIに「求人文を書いて」と頼んで終わりではない。

AIが作った投稿文が、案件条件、地域、給与、在宅なのか工場なのか、公式LINEの扱い、使ってはいけない表現に合っているかを確認する。

NGなら、NGのものだけ再作成する。

人間が見るべきなのは、全件の文章ではなく、問題があるもの、判断が必要なもの、反映前のもの。

だから操作画面では、状態を見えるようにしている。

画像生成タブでは、アカウントごとに工場、在宅1、在宅2の画像状態を並べて確認する。


ここでは、各枠に「検証OK」「確認済み」「スプレッドシート未反映」のような状態が出る。

検証という言葉も少し硬いけど、やっていることはシンプル。

「工場の投稿なのに在宅っぽい画像になっていないか」
「在宅の投稿なのに工場の写真になっていないか」
「投稿文と画像の内容がズレていないか」

こういう間違い探しをしているだけ。

画像をまとめて作る。
まとめて確認する。
NG投稿文を再作成する。
NG画像だけ再生成する。
Google Driveに入れる。
シートへ反映する。
画像履歴を見る。
画像登録を取り消す。

こういう操作を、アカウント別・求人種別別にできる。

右側には、画像の雰囲気をそろえるための型も置いている。

工場画像と在宅画像では、見せたい印象が違う。

工場なら、現場感、働くイメージ、安心感。
在宅なら、家で働けること、スマホやPCで完結すること、完全在宅であること。

だから画像の指示文も型にして、全体の雰囲気をそろえる。

アプリは、その型と作った画像をつなぐ管理画面になっている。

さらに、実行ログタブもある。


これは地味だけど、運用ではかなり重要。

AIや自動化は、必ずどこかで失敗する。

画像生成が失敗する。
Google Driveへの保存が失敗する。
スプレッドシート認証が切れる。
投稿文の確認でNGが出る。

そのときに、チャットの履歴だけを追うのはつらい。

だからアプリ側で、実行ログ、失敗状態、改善予定を残す。

ログというのは、作業の記録のこと。

宅配便で言うと「いつ発送されたか」「どこの営業所を通ったか」「配達に失敗したか」が残る追跡履歴に近い。

自動化でも、どこで止まったかが分からないと直せない。

裏側では、`outputs/jmty-gui/` に状態を記録するファイルを置いている。

`sheet_cache.json` にはスプレッドシートから読んだ情報。
`image_validation.json` には画像確認の結果。
`approvals.json` には承認状態。

週次生成物そのものは、`outputs/jmty-weekly/current/` に置く。

つまり、ジモティーアプリは、データをアプリ内に閉じ込めていない。

投稿文、画像の指示文、画像、確認結果、承認状態、ログをファイルとして残し、それを画面から操作できるようにしている。

アカウントごとに、工場、在宅1、在宅2の投稿文と画像を並べて確認する。

生成済みか。
画像はあるか。
投稿文と画像の内容は合っているか。
Google Driveに入れてよいか。
スプレッドシートへ反映済みか。
どこでエラーが出たか。

こういう運用上の確認を、毎回フォルダを開いて目視するのはしんどい。

だから操作画面では、`inputs/` と `outputs/` のファイルを読み取り、アカウント別・求人種別別に状態を見せる。

必要なら、投稿文だけを開く。
画像だけを確認する。
承認状態を保存する。
スプレッドシートに入れる前のチェックをする。
失敗した工程を改善レポートに残す。

ただし、操作画面が本質なのではない。

操作画面はあくまで、`inputs/` と `outputs/` のファイルを読み書きするためのもの。

本質は、AIが読む素材と、AIが出す成果物がファイルとして整理されていること。

ジモティーでAIに渡している前提知識はこう。

- 案件情報
- 工場求人の条件
- 在宅求人の条件
- 投稿地域
- 投稿地域の入れ替えルール
- 投稿文スタイル見本
- 画像の雰囲気をそろえる型
- 公式LINEの扱い
- 実URLを出さないルール
- 在宅なら「完全在宅」と明記するルール
- 工場画像と在宅画像を取り違えない確認ルール

ここで面白いのは、AIに「文章作成」だけを任せていないこと。

投稿文を作る。
画像を作るための指示文を作る。
画像を作る。
画像と投稿文が合っているか確認する。
Google Driveに入れる。
スプレッドシートに反映する。
失敗したら改善レポートを残す。

ここまでをファイル構造と手順に落としている。

だから、ただの投稿文生成ではなく、週次運用にできる。

事例3: LP制作

LP制作も同じ。

LPは、商品や講座を申し込んでもらうためのページのこと。

正式にはランディングページと言ったりする。

こんな言葉、普段Web制作をしていない人からすると分かりにくいと思う。

簡単に言うと「広告や投稿を見た人が最初にたどり着く、申し込み用の縦長ページ」。

いきなり「売れるLPを作って」と言っても弱い。

LPでは、ページの中身をセクションごとに分けて、原稿、画像プロンプト、生成画像、リンク領域、修正履歴を分けている。

セクションというのは、ページの中のひとまとまりのこと。

たとえば「最初に見せる部分」「悩みを見せる部分」「料金を見せる部分」「よくある質問」みたいな区切り。

画像プロンプトは、画像を作るための指示文。

リンク領域は、画像の中でクリックできる場所。

専門用語っぽく聞こえるけど、要するにLPを部品ごとに分けて管理しているだけ。

構造はこう。

```text
LPデザイン/
|-- projects/
|   `-- ai-income-course/
|       |-- LP原稿.md
|       |-- section-image-prompts.md
|       `-- ver01-fresh-green/
|           |-- score-log.md
|           |-- section-image-prompts.md
|           `-- lp/
|               |-- index.html
|               |-- link-areas.json
|               |-- copy/
|               |   `-- lp-copy-v3.md
|               |-- images/
|               `-- assets/
|
|-- .lp-editor/
|   |-- generated-prompts/
|   |-- compositions/
|   |-- operations/
|   |-- state-snapshots/
|   |-- history/
|   |   |-- SEC-01/
|   |   |-- SEC-02/
|   |   `-- SEC-08/
|   `-- ref-images/
|
|-- skills/
|   `-- lp-design/
|       |-- lp-version-creator/
|       `-- image-prompt-generator/
`-- docs/
```

LPで重要なのは、1枚のページとして考える前に、セクションごとに分けること。

LPは縦に長い。

だから、AIに丸ごと作らせるより、

- 最初に見せる部分
- 読者の悩み
- なぜ今やるべきか
- 事例
- お客様の声
- 講座内容
- 参加するメリット
- キャンペーン
- よくある質問
- 最後の申し込み案内

のように分けた方が圧倒的に扱いやすい。

部屋の片付けと同じ。

服、本、書類、充電器を全部同じ箱に入れると、あとで探すのが大変になる。

LPも同じで、全部を1つのかたまりにすると、どこを直せばいいか分からなくなる。

実際、LP用の手順書では、LP原稿を読み、見た目の方向性を決め、セクションごとに画像プロンプトを作る流れにしている。

```text
LP原稿.md
    ↓
デザインテーマを決める
    ↓
セクションごとに画像プロンプト化
    ↓
画像を生成
    ↓
LP画像として並べる
    ↓
リンク領域を設定
    ↓
履歴を残して改善する
```

LP制作にも、セクションごとに編集するアプリを作っている。


この画面では、LP全体を一気に直すのではなく、1セクションずつ扱う。

左に原稿。
中央に画像プロンプト。
右に生成された画像。

この3つを横並びにしている。

なぜかというと、LP画像の失敗はだいたいこの3つのどこかで起きるから。

原稿で伝えたいことが曖昧なのか。
画像プロンプトが弱いのか。
画像は綺麗だけど、その場所で伝えたいこととズレているのか。

これをチャットだけで見ようとすると、かなり面倒になる。

アプリでは、セクションを検索し、最初の見せ場やよくある質問のような単位で開き、原稿を見ながら画像プロンプトを直し、画像を見て採用するか判断できる。


さらに、参考画像の管理、画像プロンプトの作り直し、全体状態の確認、公開中LPの確認、公開サービスへの反映まで同じ画面からできるようにしている。


裏側の構造は、さっき見せた `.lp-editor/` が担っている。

`generated-prompts/` には生成した画像プロンプト。
`compositions/` にはセクションの並びや構成。
`operations/` には操作ログ。
`state-snapshots/` にはその時点の状態。
`history/` にはセクションごとの変更履歴。
`ref-images/` には参照画像。



公開するLP本体は、プロジェクト配下の `lp/` に置く。

つまり、アプリはLPを直接ぐちゃぐちゃに編集しているわけではない。

原稿、画像プロンプト、画像、履歴、公開用LPを分けたうえで、それらを1つの操作画面にまとめている。

ここでも大事なのは、AIに完成品だけを求めていないこと。

原稿、画像プロンプト、生成画像、履歴、リンク領域を分けている。


だから、後から

「最初の見せ場だけ作り直して」
「特典画像だけ別の雰囲気にして」
「このバージョンのデザインだけ変えて」

ができる。

LP制作でAIに渡すべき前提知識はこう。

- 商品情報
- ターゲット
- 価格
- 申し込みや登録など、最後にしてほしい行動
- LP原稿
- ページの構成
- 参考LP
- デザインテーマ
- 画像の比率
- 画像内に入れるコピー
- 避けたい表現
- どのまとまりを何の目的で見せるか

LPでの良い見本は、売れているLP、参考にしたいデザイン、反応が取れているファーストビュー、過去に使えたコピー。

これをファイルにしておくと、AIは「なんとなく綺麗なLP」ではなく、狙いのあるLPを作りやすくなる。

事例4: 法人研修コンテンツ

法人研修は、さらに資料棚の力が出る。

なぜなら、必要な成果物が多いから。

スライド案、講師台本、画像を作るための指示文、スライド画像、ワークシート、配布資料、演習データ、出典メモ。

これをチャットだけで管理しようとすると、すぐ破綻する。

だから、講座単位、全体単位、各回単位で分けている。

```text
AI法人研修/
|-- skills/
|   |-- corporate-training-course-builder/
|   `-- gws-ai-training-slide-exporter/
|
|-- スライド/
|   |-- スライド生成テンプレート選択フロー.md
|   `-- テンプレート/
|
|-- 素材/
|   `-- ロゴ/
|
|-- 講座/
|   `-- <講座名>/
|       |-- 全体/
|       |   |-- 講座概要.md
|       |   |-- 詳細シラバス.md
|       |   |-- 全回講師用メモ.md
|       |   |-- 全回ワークシート.md
|       |   |-- 演習データ回別一覧.md
|       |   `-- 調査/
|       |
|       |-- 01-<第1回タイトル>/
|       |   |-- スライド案.md
|       |   |-- 講師台本.md
|       |   |-- 画像生成プロンプト.md
|       |   |-- ワークシート.md
|       |   |-- 配布資料/
|       |   |-- 演習データ/
|       |   |-- スクリーンショット/
|       |   `-- スライド画像/
|       |
|       |-- 02-<第2回タイトル>/
|       |-- 03-<第3回タイトル>/
|       `-- 06-<第6回タイトル>/
|
`-- 非公開/
    |-- 法人研修Drive原本/
    `-- 法人研修Drive抽出テキスト/
```

ここでの工夫は、`全体/` と `各回/` を分けていること。

`全体/` には、講座全体の目的、シラバス、全回の流れ、調査メモ、演習データ一覧を置く。

各回のフォルダには、その回で使うものだけを置く。

これが大事。

各回に同じCSVや同じ資料を雑にコピーすると、AIも人間も混乱する。

第1回で使う演習データと、第4回で使う演習データは違う。

だから、各回の `演習データ/` には、その回で本当に使うものだけを入れる。

そして、講師台本には、

- どのスライドで何を話すか
- どこで画面共有するか
- 何分くらい見せるか
- 受講者にどこで動画を一時停止してもらうか
- どの演習データを使うか
- うまく進まなかったときの代わりの説明は何か

まで書く。

AIに任せる範囲を「資料作成」ではなく「研修を進めるために必要なもの一式」にしている。

だから、講座をもう1つ作りたいときは、新しい講座フォルダを作れば同じ構造で増やせる。

これが、あとから増やしやすい形。

4つに共通する本質

X、ジモティー、LP、法人研修。

全部違う仕事に見えるけど、共通点はこれ。

```text
AIに渡す前提知識
    +
AIに見せる良い見本
    +
AIが読む手順書
    +
AIが保存する場所
    +
AIと人間が確認する方法
```

これをフォルダとファイルの形にしているだけ。

逆に言うと、AIに仕事を任せられない人は、ここがない。

毎回チャットに、

「いい感じに書いて」
「もっと自然にして」
「売れそうにして」
「バズりそうにして」

と頼んでいる。

でも、AIからすると判断材料が足りない。

誰に向けるのか。
何を売るのか。
どんな表現はOKなのか。
どんな表現はNGなのか。
過去に何がうまくいったのか。
どこに保存するのか。
どう確認するのか。

これがないと、AIは一般論で返すしかない。

アプリは、ファイル構造の上に載せる操作レイヤー

ここまで見ると、僕が作っているアプリはかなり大きな仕組みに見えるかもしれない。

でも、考え方はシンプル。

操作レイヤーという言い方をすると、ちょっと難しく聞こえると思う。

簡単に言うと「人間が触るための画面」のこと。

裏側にはファイルや手順があって、その上にボタンや一覧画面を載せている。

スマホで言うと、写真データそのものは本体の中にある。

でも、僕たちは写真アプリの画面から見たり消したりする。

それと同じ。

アプリは、AIの代わりに考えるものではない。

AIが読めるフォルダ分けと、人間が判断しやすい画面をつなぐもの。

構造としてはこう。

```text
画面
    ↓
操作ボタン・編集フォーム
    ↓
裏側で動く処理
    ↓
前提知識 / アカウント情報 / 見本 / 手順書を読む
    ↓
成果物 / 作業用フォルダ / 履歴 / ログに保存する
    ↓
必要に応じて X / Google Drive / スプレッドシート / 公開サービス / メモ保管場所に反映する
```

画面の役割は、AIに丸投げすることではない。

むしろ、人間が判断しやすくすること。

たとえばX下書きアプリなら、AIが作ったスレッドを一覧で見て、1投稿ずつ直し、投稿前チェックを通し、投稿済みとして管理する。

LPの編集アプリなら、原稿、画像プロンプト、画像を並べて見て、どの部分だけ作り直すかを決める。

ジモティーの操作画面なら、アカウントごとに投稿文と画像を確認し、Google Driveやスプレッドシートへ反映する前に状態を揃える。

つまり、アプリでできることは主にこのあたり。

- 生成物を一覧で見る
- アカウント別、案件別、セクション別に絞り込む
- 1つの成果物だけを編集する
- AI修正や画像プロンプトの作り直しを部分的にかける
- 投稿前・公開前のチェックをする
- 採用、保留、投稿済み、公開済みなどの状態を保存する
- 作業履歴や改善点を残す
- 外部サービスへ反映する前の確認画面にする

ここで大事なのは、アプリを最初に作る必要はないということ。

最初はフォルダとメモファイルだけでいい。

でも、同じ作業を何度も繰り返すようになったら、アプリを作る価値が出てくる。

毎回ファイルを探す。
毎回どれが最新か確認する。
毎回同じチェックをする。
毎回同じ保存先に置く。

この繰り返しが増えたら、そこを画面化する。

だから僕にとってアプリは、AI活用の出発点ではなく、作業が回り始めたあとの管理画面。

フォルダ分けが先。

アプリはその上に載る。

まず真似するなら、この構造でいい

いきなり僕と同じ構造にする必要はない。

まずは、どんな業務でもこの形にすればいい。

```text
my-agent-work/
|-- 00_goal.md
|-- 01_context/
|   |-- business.md
|   |-- target.md
|   |-- product.md
|   `-- funnel.md
|
|-- 02_examples/
|   |-- good_examples.md
|   |-- bad_examples.md
|   `-- analysis.md
|
|-- 03_rules/
|   |-- writing_rules.md
|   |-- design_rules.md
|   |-- compliance_rules.md
|   `-- ng_words.md
|
|-- 04_workflow/
|   |-- agent_instructions.md
|   |-- output_format.md
|   `-- validation_checklist.md
|
|-- 05_outputs/
|   |-- drafts/
|   |-- images/
|   `-- final/
|
|-- 06_app/                    # 必要になったら操作画面
|   |-- screen_notes.md
|   `-- operations.md
|
`-- 99_logs/
    |-- feedback.md
    `-- improvement_notes.md
```

このフォルダを作って、AIにこう渡す。

ここでは `context` や `workflow` みたいな英語も出てくる。

contextは「背景情報」。

workflowは「作業の流れ」。

横文字にすると難しく見えるけど、実際には「先にこれを読んで、次にこれをやって」という順番を書いているだけ。

```text
この仕事をAIに任せたいです。

まず `00_goal.md` を読んで、この仕事の目的を把握してください。
次に `01_context/` の前提知識を読んでください。
次に `02_examples/` の良い例と悪い例を比較し、判断基準を作ってください。
次に `03_rules/` のルールを守ってください。
作業手順は `04_workflow/agent_instructions.md` に従ってください。
作ったものは `05_outputs/` に保存してください。
操作画面がある場合は `06_app/operations.md` の役割分担に従ってください。
作業後、`04_workflow/validation_checklist.md` に沿って確認し、
気づいた改善点を `99_logs/improvement_notes.md` に残してください。
```

これだけで、AIへの任せ方がかなり変わる。

「投稿を作って」ではなく、

「この資料棚を読んで、ルールに従って、指定の場所に保存して、確認して、改善点を残して」

になる。

これがAIに仕事を渡すということ。

僕が実際にやっている工夫

今回見せた構造の中で、特に大事な工夫はこの8つ。

1つ目は、読む材料と作ったものを分けること。

`inputs/` や `accounts/` はAIに読ませる材料。
`outputs/` や `runtime/` はAIが作った成果物。

ここを混ぜない。

2つ目は、実運用と公開用を分けること。

X運用では `private` と `public` を分けている。

実アカウント情報、ログ、ブックマーク、生成物は公開しない。

配布できるコードやサンプルだけを公開側に置く。

3つ目は、アカウント別・案件別・講座別に分けること。

1つの巨大ファイルに全部入れると、AIが混乱する。

Xならアカウント別。
ジモティーならアカウント別・求人種別別。
LPならプロジェクト別・ページ内のまとまり別。
研修なら講座別・各回別。

4つ目は、良い見本とルールを分けること。

良い見本は「こういう方向が正解」。
ルールは「これは守る」「これはやらない」。

似ているけど役割が違う。

5つ目は、画像の指示文を成果物として保存すること。

画像だけ保存しても、次に再現できない。

指示文も残すから、もう一度作る、直す、別パターンを出す、ができる。

6つ目は、確認結果と改善メモを残すこと。

AIに作らせて終わりにしない。

ジモティーなら投稿文と画像条件が合っているか。
LPなら、その場所で伝えたいことと画像が合っているか。
研修ならスライド、台本、演習データが一致しているか。

確認した結果や失敗理由を残す。

7つ目は、手順をスキル化すること。

スキル化という言葉も、初めて聞くと分かりにくいかもしれない。

僕の中では「毎回同じ説明をしなくていいように、手順書として保存しておくこと」。

家電の説明書を毎回店員さんに聞かなくても、説明書を見れば使えるのと同じ。

AIに毎回同じ説明をするのではなく、`SKILL.md` や `agent_instructions.md` にしておく。

すると次回からは、

「この手順書に従って」
「このフォルダを読んで」

だけで動ける。

8つ目は、アプリをファイル構造の上に載せること。

アプリを作るときも、アプリの中にすべてを閉じ込めない。

前提知識は `inputs/`。
見本は `samples/`。
手順は `skills/`。
成果物は `outputs/`。
履歴は `history/` や `logs/`。

アプリはそれらを読み書きする操作画面にする。

この形にしておくと、アプリを直すときも、AIに作業を任せるときも、データの場所が分かりやすい。

画面が変わっても、成果物や履歴がファイルとして残る。

これが、あとから改善できる運用になる。

AI力と人間力の分担

ここまで聞くと、AIが全部やっているように見えるかもしれない。

でも、違う。

AIが得意なのは、速く作ること。

人間がやるべきなのは、正解を選ぶこと。

AIは投稿文を大量に作れる。
でも、どの投稿が自分のブランドに合うかを決めるのは人間。

AIは求人画像を作れる。
でも、どの画像が応募者に誤解を与えないかを決めるのは人間。

AIはLP画像を作れる。
でも、どの見せ方が申し込みにつながるかを決めるのは人間。

AIは研修資料を作れる。
でも、どの構成が受講者の実務に効くかを決めるのは人間。

だから、AI時代に必要なのは「全部AIに丸投げする力」ではない。

AIが判断できるだけの材料を渡し、人間が正解を選べる状態を作る力。

これが本質だと思っている。

今日からやるなら、最初の一歩はこれ

自分の業務で、まず1つだけ選んでほしい。

投稿作成でもいい。
求人文作成でもいい。
LP作成でもいい。
研修資料でもいい。
営業メールでもいい。
議事録でもいい。

そして、いきなりAIに作らせる前に、次の3つをファイルにする。

```text
01_前提知識.md
02_良い見本.md
03_作業ルール.md
```

`01_前提知識.md` には、自分の事情を書く。

誰に向けるのか。
何を売るのか。
読者をどこへ案内したいのか。
どういう口調なのか。
守るべき制約は何か。

`02_良い見本.md` には、うまくいったものを貼る。

伸びた投稿。
売れたLP。
応募が来た求人文。
合格した資料。
参考にしたいデザイン。

`03_作業ルール.md` には、やってほしいこととNGを書く。

文字数。
構成。
避けたい表現。
保存先。
確認方法。
修正の基準。

この3つだけでも、AIが作るものはかなり変わる。

AIに渡す文章はこうでいい。

```text
この3つのファイルを読んでから作業してください。

`01_前提知識.md` は、この仕事の背景です。
`02_良い見本.md` は、目指す方向です。
`03_作業ルール.md` は、守るべき条件です。

まず3ファイルを読んで、今回の仕事で重要な判断基準を5つに整理してください。
その後、成果物を作ってください。
最後に、どの判断基準をどう反映したかを説明してください。
```

これだけで、AIはただの文章づくりツールではなく、仕事の背景を読んで動く相手になる。

まとめ

AIに仕事を任せる技術は、派手なものではない。

やっていることはかなり地味。

前提知識を置く。
良い見本を置く。
ルールを置く。
手順を置く。
保存先を決める。
確認方法を決める。
改善点を残す。

でも、この地味な設計があるかどうかで、AI活用の再現性は大きく変わる。

AIに仕事を任せるとは、

「すごい指示文を書くこと」

ではなく、

「AIが迷わず動ける資料棚を作ること」

だと思っている。

今回の記事では、僕が実際に使っているX運用、ジモティー、LP制作、法人研修のフォルダ分けを見せながら、AIへの仕事の渡し方を具体的に話しました。

この記事は、実践編です。

一方で、もっと前提にある

「なぜプロンプトだけでは成果が出ないのか」
「なぜAIに前提知識と作業場所を渡す必要があるのか」
「コンテキストエンジニアリングやハーネスエンジニアリングとは何か」

という本質的な話は、前回の長文記事でかなり詳しく書きました。

コンテキストエンジニアリングとか、ハーネスエンジニアリングとか、正直いきなり言われてもよく分からない人が多いと思う。

簡単に言うと、

コンテキストエンジニアリングは「AIに渡す前提知識を整えること」。

ハーネスエンジニアリングは「AIが作業しやすい道具や作業場を整えること」。

今回の記事で見せたフォルダ分けやアプリは、まさにその具体例です。

今回の記事を読んで、

「なるほど、実際にはこういうフォルダ分けでやるのか」

と思った人は、前回の記事も読むと、なぜこの構造が大事なのかがさらに理解できると思います。
